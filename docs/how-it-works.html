THE EXECUTION
PIPELINE

Scrumb operates as a state machine for project birth and survival. Your project cannot advance to the next stage until the current one clears. No shortcuts. No hand-waving. Here's how each stage works.

01
ARCHITECT_AUDIT
GATE ACTIVE

THE ARCHITECT AUDIT

Before a single task is created, the Architect Prime AI interrogates your idea. You describe the project in plain English. Scrumb responds with a series of technical multiple-choice questions designed to surface every assumption your team hasn't articulated yet.

Stack choices get locked. Team skill levels get logged. MVP scope gets bounded. The questions are uncomfortable on purpose — because "we'll figure it out" is how projects fail at hour 36 of a 48-hour hackathon.

  • Tech stack selection locked via MCQ (FastAPI vs Django, React vs Vue, etc.)
  • Team skill matrix recorded — tasks assigned to real capability, not aspiration
  • MVP boundary defined before any architecture decisions are made
  • Scope creep vectors identified and flagged before the build starts
// EXAMPLE AUDIT EXCHANGE ARCHITECT_PRIME: "Your team includes a Python dev and a React dev.
  For the backend, which of these matches their experience?"
  A) FastAPI + SQLite (familiar, fast)
  B) Django REST + PostgreSQL (powerful, slower start)
  C) Express.js (wrong team for this)

USER: A

// Stack locked. Generating task tree for FastAPI architecture...
02
DAG_GENERATOR
GATE ACTIVE

DAG GENERATION

Based on the Architect Audit, Scrumb generates a Directed Acyclic Graph of every task in your project. This is not a flat to-do list. Every task in the DAG knows three things: what it depends on, what depends on it, and who owns it.

Owners are auto-assigned based on the skill matrix captured in Stage 01. The critical path — the chain of tasks where any delay cascades — is calculated and highlighted. You see exactly what has to happen first, and why.

  • Full dependency graph — no task is an island
  • Critical path identified and surfaced prominently
  • Owners assigned based on actual team skills, not just availability
  • Timeline estimated from task complexity + team velocity
  • Integrity Guard pre-armed: parent tasks locked until children complete
// EXAMPLE DAG FRAGMENT [ setup/db-schema ] → [ backend/user-auth ] → [ backend/api/endpoints ]
                                      ↓
                        [ frontend/dashboard ] ← BLOCKED

Owner: @Rohan (Python) · Est: 3hrs · CRITICAL PATH
03
ACTIVE_BUILD
GATE ACTIVE

ACTIVE BUILD

Your team is building. Scrumb surfaces the task tree directly inside your JetBrains IDE — no tab switching to check what needs to happen next. Each developer sees their tasks, their blockers, and the downstream impact if they fall behind.

The Integrity Guard runs continuously during this phase. It is not possible to mark a parent task complete while its sub-tasks are still open. The dashboard always reflects reality.

  • Task tree visible in JetBrains sidebar — no context switching
  • Each task shows: owner, estimate, dependencies, downstream impact
  • Integrity Guard blocks dishonest task completion
  • Velocity tracked automatically as tasks complete
04
DRIFT_DETECTION
GATE ACTIVE

DRIFT DETECTION

Scrumb continuously compares actual velocity against the deadline. When the math stops working, two systems activate based on the type of problem detected.

Panic Mode activates when scope exceeds timeline. It analyzes the remaining task tree, identifies which tasks are critical for a working demo, and archives everything else. The MVP shrinks to what can actually be built.

The Shame Engine activates when a specific task has been stalled for too long — especially when it's on the critical path. It generates a named accountability report directed at the person responsible. Brutal. Funny. Effective.

  • Panic Mode: AI-driven scope trim, non-critical tasks archived automatically
  • Shame Engine: named, task-specific accountability reports
  • Both can activate simultaneously if the situation warrants it
  • All drift interventions are logged for post-project retrospective
05
MVP_SHIPPED
TARGET STATE

MVP SHIPPED

The project compiles. Not necessarily perfect — but finished, functional, and defensible. The scope that shipped is the scope that was achievable. Panic Mode trimmed what wasn't. The team can explain every decision because the Architect Audit forced those decisions to be made explicitly.

Scrumb generates a post-project summary: what shipped, what was archived, where time was lost, and what the team's real velocity was. This data feeds better estimation on the next project.

  • Post-project report: shipped scope, archived tasks, velocity data
  • Retrospective insights surfaced automatically — no meeting required
  • Team velocity profile updated for more accurate future estimation
