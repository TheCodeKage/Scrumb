GETTING STARTED

INSTALLATION

The Scrumb plugin installs directly into any JetBrains IDE from disk. No marketplace listing yet — this is early access.

Supported IDEs

IntelliJ IDEA

Java, Kotlin, Scala, Groovy

PyCharm

Python, Django, Flask, FastAPI

WebStorm

JavaScript, TypeScript, React, Vue

GoLand

Go, microservices, CLI tools

Install Steps

  1. Download the plugin zip — scrumb-plugin.zip
  2. Open your JetBrains IDE
  3. Go to File → Settings (Windows/Linux) or JetBrains IDE → Preferences (macOS)
  4. Navigate to the Plugins section
  5. Click the ⚙ gear icon in the top-right corner of the Plugins panel
  6. Select Install Plugin from Disk…
  7. Select the downloaded scrumb-plugin.zip file
  8. Restart the IDE when prompted
  9. Scrumb appears in the right sidebar panel after restart
Note: If the Scrumb panel doesn't appear after restart, go to View → Tool Windows → Scrumb to manually open it.
PREREQUISITES

REQUIREMENTS

  • ✓ JetBrains IDE version 2023.1 or later
  • ✓ Internet connection (for AI calls during Architect Audit and Shame Engine)
  • ✓ No additional accounts or API keys required during early access
FIRST TIME SETUP

FIRST RUN

After installation, open the Scrumb panel from the right sidebar. You'll see the main interface with your project state.

To start a new project, click New Project and Scrumb will launch the Architect Audit — a short technical interview that generates your task dependency graph. The audit takes 3–5 minutes.

Tip: Have your team's skill levels ready before starting the Architect Audit. The more accurate the skill matrix, the better the task assignments.
MODULE 01

ARCHITECT AUDIT

The Architect Audit is the entry gate for every Scrumb project. It cannot be skipped. It works by asking you a sequence of technical multiple-choice questions about your project, stack, team, and timeline.

Questions adapt based on your answers. A Python-only team gets different stack questions than a full-stack team. A 48-hour hackathon gets different scope questions than a 2-week sprint.

What it captures

// AUDIT OUTPUT SCHEMA
project.name = "Bus tracking app"
project.deadline = "48hrs"
project.team = [
  { name: "Priya", skills: ["Python", "FastAPI", "SQL"] },
  { name: "Rohan", skills: ["React", "TypeScript"] },
  { name: "Aditya", skills: ["Python", "ML"] }
]
stack.backend = "FastAPI" // locked via MCQ
stack.frontend = "React" // locked via MCQ
mvp.scope = ["auth", "real-time-bus-location", "basic-ui"] // bounded
mvp.descoped = ["analytics", "admin-panel", "notifications"] // deferred
Warning: Vague project descriptions produce vague task graphs. If your answer to "What does the MVP need to do?" is "a bunch of stuff," the Architect will ask again.
MODULE 02

DAG GENERATOR

After the Architect Audit completes, Scrumb generates a Directed Acyclic Graph of all project tasks. Every task in the graph has:

task {
  id: "backend/auth/jwt-middleware"
  owner: "@Priya"
  estimate: "3hrs"
  depends_on: ["setup/db-schema"]
  blocks: ["backend/api/user-endpoints", "backend/api/routes"]
  critical_path: true
  status: "BLOCKED" // waiting on dependency
}

Tasks are displayed in the IDE sidebar. Each developer sees only their assigned tasks and the tasks they're blocking or waiting on. The full graph is always accessible from the project view.

MODULE 03

PANIC MODE

Panic Mode activates automatically when Scrumb detects that remaining task volume cannot be completed before the deadline at current velocity.

It analyzes the task tree and separates tasks into two buckets:

CRITICAL (keep): tasks required for a working, demoable MVP
NON-CRITICAL (archive): tasks that improve the product but aren't required for demo

// Archived tasks are preserved, not deleted. They can be restored post-deadline.

Panic Mode can also be triggered manually from the Scrumb panel if the team decides to scope down proactively.

Tip: Trigger Panic Mode early if you're behind. Scope decisions made at T-12hrs are always better than scope decisions made at T-2hrs.
MODULE 04

SHAME ENGINE

The Shame Engine monitors task stall times and generates named accountability reports when thresholds are exceeded. It is disabled by default and must be explicitly enabled per team.

See the full Shame Engine documentation for configuration options, example reports, and escalation logic.

Warning: Enable Shame Engine with team agreement. Activating it unilaterally is a bad idea and possibly a worse look.
MODULE 05

INTEGRITY GUARD

Integrity Guard prevents marking a parent task as complete if any of its sub-tasks remain open. It runs continuously and cannot be disabled.

// INTEGRITY GUARD — BLOCKED ACTION
ACTION: mark [ backend/api ] as DONE
RESULT: BLOCKED
REASON: 2 sub-tasks still open:
  ✗ [ backend/api/auth-endpoints ] — IN_PROGRESS
  ✗ [ backend/api/data-validation ] — NOT_STARTED

// Complete sub-tasks before marking parent done.
REFERENCE

SETTINGS

SETTING DEFAULT DESCRIPTION
SHAME_ENGINE OFF Enable named stall accountability reports
SHAME_THRESHOLD 48hrs Stall duration before report generates
PANIC_AUTO ON Auto-trigger Panic Mode when velocity math fails
INTEGRITY_GUARD ON (locked) Cannot be disabled
SHAME_TONE BRUTAL_FUNNY Options: BRUTAL_FUNNY, DIRECT, PROFESSIONAL
SHAME_DELIVERY TEAM_CHANNEL Options: TEAM_CHANNEL, PRIVATE_DM
